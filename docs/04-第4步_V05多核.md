## 相对 V04 改了什么

把工作切成 (batch, M 块) 的 chunk，`chunkCount = B * ceil(M/baseM)`，按 `blockIdx` 循环分配给 `min(availableCoreNum, chunkCount)` 个核。

四个避免竞争的设计：

1. **每核独占 tile 切片**。`tileStorage` 按 `coreIdx * TILE_M * TILE_N` 切分，并发的 `GetTensorC` 写入目标互不重叠。
2. **每 chunk 独占 64 字节槽位**（`SLOT = 16` 个 float）。并行阶段任意两个核都不会写到同一条 cache line —— 这正是 V02 注释里警告的那个坑。
3. **一次 `SyncAll()` 屏障**。所有启动的 block 无条件到达：没分到 chunk 的核直接跳过循环落到屏障，不会提前 return 造成挂死。
4. **只有 block 0 写 `y`**。单写者，彻底排除输出端的 cache line 竞争。

仍然是**单次 kernel 启动**，规则 12 不受影响。Host 只做 tiling、切分和启动配置。

## 预期收益

Cube 路径提速上限是 `min(核数, chunkCount)` 倍。

| B | M | chunkCount | 可用核数(设48) |
|---|---|---|---|
| 1 | 1000 | 8 | 8 |
| 1 | 8192 | 64 | 48 |
| 8 | 512 | 32 | 32 |
| 64 | 20 | 64 | 48 |
| 2 | 4096 | 64 | 48 |

**B=1 且 M<128 时 chunkCount=1，多核没有收益。** 这种形状需要按 N 方向并行，留到 V06。

## 唯一未核实的 API

`AscendC::SyncAll()` 的确切签名没有对照真实 CANN 9.0.0 头文件核实过。除它之外，V05 用到的全部接口都在 V04 里编译并通过了 15 点：`GetBlockIdx()`（官方 matmul 示例里也在用）、`DataCacheCleanAndInvalid`、`Matmul` 系列、`GlobalTensor::operator[]`。

**如果编译失败，第一处 error 大概率就指向这一行**，改一处即可。失败是响亮的（编译期），不会静默算错。

## 本地验证范围

`learning/validate_v05_cpu.py`，结果 `research/v05_cpu_model.json`。

- 17 组 shape × 2 dtype × 4 转置 × 2 数据分布 × **6 种核数(1/2/3/7/20/48)** = **1632 组检查全部通过**。
- **272 组核数不变性检查：同一输入在不同核数下输出逐位相同。** 这证明 chunk 分配、槽位 padding、core-0 汇总不依赖执行顺序。
- mock 把各核**乱序回放、block 0 放最后**，不是顺序执行。
- 断言每个启动的 block 都到达屏障（`syncs == blocks_run`）。
- 两种 `GetTensorC` 行间距约定下结果一致，尾块数仍为 0。
- 最大绝对误差 `2.44e-4`。

CPU 模型**不验证真实 CANN 头文件、目标编译器、Matmul 内部调度、真实并发、缓存一致性或性能**。多核是按"各核写入互不重叠所以顺序无关"来建模的；真机上的 cache line 粒度与屏障语义仍需实测确认。
