## 相对 V03 改了什么

1. **Cube 核函数改为 `__aicore__`，删除 `#define ASCENDC_CUBE_ONLY`**。官方 CANN 9.0.0 Matmul 示例用的是 `__aicore__`；原来的写法同时堵死了后续 Vector 归约。标量核函数保持 `__cube__` 不变，那是已通过 6 点的路径。
2. **`SetOrgShape` 改为四参形式** `SetOrgShape(M, N, K, K)`。转置操作数需要正确的 leading dimension，三参形式是否能推导出来没有依据。
3. **N 方向全宽分块**。最后一块不再变短，而是回退到起点 `N - baseN`。因为 N 方向做的是取最大值，重复计算同一列不改变结果。这样 `GetTensorC` 永远只写满宽 tile，它对尾块的行间距约定是 `baseN` 还是实际宽度就不再影响答案。
4. **Host 侧校验 `baseM` / `baseN`**。不符就在启动之前返回 false 回退标量路径。原来的 device 侧 `return` 会让 `y` 一个字节都不写，结果取决于输出缓冲里的残留值。
5. **`baseM` 从 16 提到最多 128**。B 面板重读次数和缓存刷新次数都降到原来的 1/8。

## 已知限制

- **仍是单核启动**。多核需要配合跨核屏障或 DMA 写回：若每个核用 `SetValue` 写自己的 `y[b]`，相邻 b 落在同一条 cache line 上，各自 `DataCacheCleanAndInvalid` 会丢更新。这一步等真机编译结果确认后再做。
- **归约仍是标量**，总量是 O(B·M·N) 次 GM 标量读。这是通不过最大测试点的根本原因，必须改成 Vector 在 UB 上归约。
- **N < 16 走标量路径**。Cube 基本块宽度是 16 的倍数，N < 16 无法构造全宽 tile。若某个大测试点的 N < 16，该点会超时。

因此 V04 的目的是**换取真机信息**，不是拿满分。重点看三件事：

1. 真实 CANN 9.0.0 能否编译通过（`__aicore__` + Matmul + 四参 SetOrgShape）。
2. 第 7 点是否完成，第 8 点及以后是否开始运行。
3. N 非对齐的点精度是否正确。

`learning/validate_v04_cpu.py`，结果 `research/v04_cpu_model.json`。

- 14 组 shape × 2 种 dtype × 4 种转置 × 2 种数据分布 = **224 组检查全部通过**，覆盖 M 尾块、N 尾块、K=8192、全负值。

这些检查用 CPU 模型替代 Matmul API，**不验证真实 CANN 头文件、目标编译器、Matmul 内部调度、硬件缓存一致性或性能**。最大工作量仍远小于实际测试点，没有已验证的加速倍数，也没有 15 点通过结果。
