## 两个硬性下限（实测）

### 1. 内核启动下限 ≈ 1.8 μs

两个判别内核，都是 `KERNEL_TYPE_AIV_ONLY`、单 block、只写输出：

| 判别版本 | 1x32x32x64 | 1x8x8x32 |
|---|---:|---:|
| `diag_floor`（用 TPipe + DataCopyPad） | 1.78 μs | 2.00 μs |
| `diag_floor2`（完全不用 TPipe，标量写 + 按行刷新） | 1.76 μs | 2.04 μs |

**`TPipe` 不是开销来源**，两者一致。约 1.8 μs 是 msprof 口径下启动与收尾的不可约成本。点 1–7 的最优是 1.17–6.36 μs，所以小形状的剩余空间有限。

### 2. Cube 路径固定开销 ≈ 9 μs

各路径实测固定成本（V36）：

| 路径 | 典型耗时 |
|---|---:|
| `bmmms_dot_kernel` | 2.91 μs（官网点 1） |
| `row_vector_kernel` | 5.54 μs（1x8x8x32） |
| `bmmms_cube_kernel` | 8.94 μs（1x32x32x64） |
| `bmmms_small_vector_kernel` | 9.76 μs（1x4x4x1024） |
| `bmmms_tiny_dots_kernel` | 11.46 μs（1x2x2x8192） |

`1x32x32x64` 的 PipeUtilization 分解（Cube 核）：

| 项 | 时间 | 占比 |
|---|---:|---:|
| scalar 执行 | 3.49 μs | 43.6% |
| 等指令取回 wait_ib | 1.36 μs | — |
| **icache 缺失率** | — | **14.7%** |
| fixpipe | 0.67 μs | 8.4% |
| mte2 | 0.65 μs | 8.2% |
| mte3 | 0.55 μs | 6.9% |
| **cube（真正的矩阵乘）** | **0.033 μs** | **0.4%** |

真正算矩阵乘只占 0.4%。Matmul API 的控制代码体量大到连指令缓存都频繁缺失。**小形状上用 Cube 必然有约 9 μs 的地板。**

## 大矩阵：吞吐随 K 变化

V36 在大形状上的实测吞吐：

| 形状 | 工作量 | 耗时 μs | GMAC/s |
|---|---:|---:|---:|
| 1x4096x4096x32 | 537M | 90.94 | **5904** |
| 64x128x128x256 | 268M | 36.30 | 7395 |
| 1x2048x2048x128 | 537M | 42.32 | 12686 |
| 1x512x512x1024 | 268M | 19.50 | 13766 |
| 8x512x512x256 | 537M | 31.32 | 17141 |
| 1x8192x256x256 | 537M | 27.82 | 19298 |
| 1x256x8192x256 | 537M | 25.88 | 20745 |
| 1x1024x1024x512 | 537M | 23.72 | 22634 |
| 2x2048x1024x256 | 1074M | 37.00 | **29020** |

K 越小吞吐越差。K=32 时只有 5904，K=256 时可达 29020。

`BmmmsCube::TryRun` 里 `int32_t boundM=64;` 是默认值，只有 `N<=64 && M>=128` 分支才放大，**所以 TILE_M=512 对大多数大形状没有生效**，baseM 实际被钉在 64。

但把 boundM 改成固定的 128 或 256 并不能通吃：

| 形状 | v36 | boundM=128 | boundM=256 |
|---|---:|---:|---:|
| 2048x2048x128 | 42.32 | **−12.9%** | **−15.1%** |
| 64x128x128x256 | 36.30 | **−10.1%** | **−9.8%** |
| 8192x256x256 | 27.82 | **−8.1%** | +4.2% |
| 4096x4096x32 | 90.94 | +15.6% | +13.0% |
| 512x512x1024 | 19.50 | +12.2% | +34.4% |
| 1024x1024x256 | 21.84 | +3.6% | +16.0% |

最优分块高度同时依赖 K 和 N。按手上这几个形状拟合规则既会过拟合，也逼近赛规第 2.8 条禁止的「逐条匹配评测用例」，因此 v41/v42 都没有提交。要继续走这条路，需要的是一个**基于 K 与 N 的通用代价模型**，并用更密的形状网格验证，而不是试参数。

## 被证伪的假设（都做了真机对照）

| 假设 | 实验 | 结果 |
|---|---|---|
| C 队列双缓冲能让 Cube 与 Vector 重叠 | V10、sw_t64x192d2 | **有害**，1024² 慢 56%，独立复现了 V10 的线上回归 |
| 会话建立开销是大矩阵瓶颈 | V16 两会话（剥离双缓冲） | **零效果**（55.00 vs 54.92） |
| 自适应 baseM 填满 24 核能提速 | V17 | 2048² 快 9.6%，1024² 慢 31%，净收益不明 |
| `ENTIRE_DATA_CACHE` 全缓存刷新是固定开销来源 | V37 按行刷新 | **零效果**，差异在噪声内 |
| 窄 N 路径应排在 Cube 之前 | V38 | **有害**，1x64x1x4096 从 174 恶化到 271 μs |
| row_vector 的派发闸门限制了覆盖面 | V39/V40 放宽 | **零效果**，`BmmmsRows::TryRun` 内部自己拒绝，闸门不是约束点 |

另有 V14（`CopyTiling` 改批量 `DataCopy`）**让内核在设备上挂死**，probe 进程 100% AICore 空转并占死 SSH 队列约 15 分钟，已作废。教训：所有远端测量命令都要加 `timeout`。

## 仍然成立的结论

- 标量路径 ≈ 35 ns/元素，严格线性。任何形状落到 `bmmms_starter_kernel` 都是灾难。
- 转置窄 N 路径（`TryRunNarrow`）在 K 小时有效（1x8x8x32 类形状提速逾千倍），**K 大时反而劣于 Cube**，所以它必须排在 Cube 之后。
- V36 的 TILE_M=512/TILE_N=256 让 1024×1024×256 从 54.92 降到 21.84 μs。
