# 第 5 步：V05b —— 修复 V05 的 Cube 路径挂死

## V05 发生了什么

提交结果：第 1、2、3 点 Pass，第 4 点 Time Limit Exceeded，第 5—15 点 Skipped。

第 1、2、3 点走标量路径（1、2 在 4096 阈值以下，3 是 N<16 回退），**完全没碰多核代码**，所以照常通过。第 4 点是第一个进 Cube 路径的测试点，一进去就超时。

结论：

- **编译是通过的**，`AscendC::SyncAll()` 存在且可编译 —— 这个事先标注的风险点已排除。
- 挂死发生在运行期，且在 Cube 多核路径入口。

第 4 点在 V04 只要 56μs，规模很小，`chunkCount` 大概率个位数，`usedCores` 很可能就是 1。**如果单 block 的 `SyncAll()` 都挂，问题就不是"某个核没到屏障"，而是屏障本身缺少初始化。**

## 两处修改

**a. 清零 workspace。** `aclrtMalloc` 不保证清零，而跨核屏障的标志位就放在传给 `__kfc_workspace__` 的那块内存里。里面是垃圾值，`SyncAll()` 就会永远自旋。现在 malloc 之后立刻 `aclrtMemset` 整块归零。

这只是初始化临时空间，所有结果仍然来自实际输入。

**b. 屏障前不再 return。** 原来的边界守卫在 `SyncAll()` 之前 `return`，任何一个 block 跳过屏障，其余到达屏障的 block 就全部挂死。现在守卫改成 `active` 标志：只跳过工作，不跳过屏障。

两处改动同时覆盖了两种可能的成因，不需要先确定是哪一种。

## 验证

`learning/validate_v05b_cpu.py` → `research/v05b_cpu_model.json`，1632 组检查全部通过。

这轮在 mock 里把 `aclrtMalloc` 改成用 `0xA5` 填充返回的内存，**漏掉 memset 会直接导致验证失败**。此外仍然保持：6 种核数结果逐位相同、两种行间距约定一致、尾块数 0、每个 block 都到达屏障。

CPU 模型仍然不验证真实并发、真实屏障语义和缓存一致性。V05b 是针对上述两个成因的修复，不是已验证的结论。

## 如果 V05b 还是 TLE

说明成因在我没覆盖的第三处（例如多 block 下 Matmul 实例与 KFC workspace 的交互）。那就**放弃 SyncAll 路线**，回到 V04 单核，改为在已验证的 API 范围内做优化：

- 调大 `baseN`，减少 tile 数量，从而减少每 tile 一次的全量 cache 刷新
- 一次把多个 N tile 写进 tile 缓冲的不同区段，攒够再刷一次 cache（`GetTensorC(tileGm[offset], ...)` 用的是已验证过的 `operator[]`）

这条路收益有上限，但不引入任何新原语。
