## 题目：算子算什么

对每个 batch，先做矩阵乘，再**对每行取最大值**，最后把这些最大值**加起来**，
输出一个标量：

```
y[b] = Σ_m ( max_n ( Σ_k X1[b][m][k] · X2[b][k][n] ) )
```

举个最小的例子。设某个 batch 的矩阵乘结果是

```
[  1   0  -1 ]   第 0 行最大值 =  1
[  0   1   0 ]   第 1 行最大值 =  1
                 y = 1 + 1 = 2
```

如果某行全是负数，比如 `[-1, -2]`，这一行的最大值是 `-1`，
不能因为累加器初始化成 0 就输出 0。这个细节在早期版本里踩过。

### 输入输出约束

| 项目 | 要求 |
|---|---|
| 输入 | 两个连续 ND 三维张量，同类型，FP16 或 BF16 |
| 逻辑形状 | `x1 = [B, M, K]`，`x2 = [B, K, N]` |
| 输出 | `y = [B]`，固定 FP32 |
| B | 1 – 64 |
| M, N | 1 – 8192，必须处理非对齐尺寸 |
| K | 32 – 8192，且是 8 的整数倍 |
| 元素总数 | `B·M·K ≤ 2^26` 且 `B·N·K ≤ 2^26` |
| 累加精度 | FP32 或等效；标准答案按输入实际存储值转 FP64 计算 |

两个输入各有独立的转置标志，描述的是**物理存储布局**，不是要你先做转置：

| `transposeX1` | `transposeX2` | x1 物理形状 | x2 物理形状 |
|---|---|---|---|
| false | false | `[B,M,K]` | `[B,K,N]` |
| false | true  | `[B,M,K]` | `[B,N,K]` |
| true  | false | `[B,K,M]` | `[B,K,N]` |
| true  | true  | `[B,K,M]` | `[B,N,K]` |

四种组合都要支持。布局直接决定哪一维在内存里连续，
而这对昇腾的搬运效率影响极大，是本题性能差异的主要来源之一。

### 规则约束

1. 完整计算必须在 NPU 上完成。Host 只能做形状、参数、切分和启动配置，不能读输入代算。
2. **一次计算只能用一次 kernel 启动。** "一个 kernel 做矩阵乘、另一个做归约"不符合规则。
3. 不得预存答案、利用未初始化内存、按输入规律跳算，或操纵预热与计时。
4. 性能分支应依据一般的规模或布局条件，并完整计算实际输入。
5. 赛后有人工核验，平台通过不等于规则核验结束。

## 为什么这题难

**一、归约把矩阵乘的输出锁在片上之外。**
普通矩阵乘算完 C 写回显存就结束了。这题还要对 C 做 `max` 再 `sum`。
昇腾的矩阵乘在 Cube 单元执行，结果落在 L0C 缓冲；
求最大值要在 Vector 单元做，而 Vector 读不到 L0C。
查 CANN 头文件确认：**910B（`__NPU_ARCH__ == 2201`）的 fixpipe 只支持
L0C→GM 和 L0C→L1，L0C→UB 只在 310 系列上存在。**
所以中间结果必须经显存兜一圈 —— 这是硬件约束，不是优化不到位。

**二、输出只有 B 个标量，固定开销占比极高。**
最小的评测点是 `B=1, M=1, N=1, K=32`，一次 32 元素的点积。
全场最优 1.20 微秒，而实测一个 MIX（Cube+Vector）内核**光启动就要 4.5 微秒**，
纯 Vector 内核也要 1.26 微秒。对这类点，战场完全在固定开销上。

**三、形状跨度五个数量级。**
从 `1×1×1×32`（32 次乘加）到 `1×1536×2048×2048`（约 64 亿次乘加），
没有任何单一策略能同时覆盖。最终版本有 23 条特化路径。

## 计分方式，以及它导致的反直觉结论

单点得分 `100 / (1 + log_1.5(t/T))`，`T` 是该点全场最优耗时，最终取 15 点均值。
打平最优得 100 分，慢 1.5 倍得 50 分，慢 2.25 倍得 33 分。

因为对 `t/T` 取了对数，**越接近最优的点，每省一微秒换到的分数越多**：

| 测试点 | 我们 / 最优 | 每省 1 μs 换多少总分 |
|---|---:|---:|
| 第 7 点 | 1.12 | **1.63** |
| 第 5 点 | 1.31 | 1.25 |
| 第 1 点 | 1.95 | 1.08 |
| … | | |
| 第 8 点 | 2.06 | 0.043 |
| 第 11 点 | 1.90 | **0.021** |

**第 7 点省 1 微秒，相当于第 11 点省 76 微秒。**
倍数最难看的大点，恰恰最不值得花时间。

这笔账项目后期才算明白。前面很多轮都在盯着倍数最差的大矩阵改，方向是错的。
完整表格见 [`final/RESULT.md`](final/RESULT.md)。

## 最终内核的结构

单文件 6696 行，23 个命名空间，10 个核函数。Host 侧 `run_kernel` 是一棵分发树，
按形状把输入导向不同实现：

| 形状特征 | 走哪条路 | 做法 |
|---|---|---|
| `M = N = 1` | `bmmms_dot_kernel` | 纯向量点积，AIV-only，启动开销最小 |
| `M·N ≤ 4` | `bmmms_tiny_dots_kernel` | 逐点积，完全不动 Cube |
| 极小 M、N | `BmmmsCompactPairs` 等 | K 作模板参数编译期展开，数据全程留在 UB |
| `min(M,N) ≤ 16` | `BmmmsRows` / `RowsSharded` | 把短边当"行"广播，纯向量算 |
| 中等规模 | `BmmmsBatchDirect` / `TailDirect` | 每 batch 直出，省掉中间归并 |
| 大矩阵 | `BmmmsMacro*` / `Mdl*` / `Cube` | Cube 分块 + AIC/AIV 手工切分流水 |
| 兜底 | `bmmms_starter_kernel` | 标量实现，保证正确性 |

大矩阵路径采用手工 AIC/AIV 切分：Cube 核算完一块 C 后经 GM 双槽交给 Vector 核归约，
用 `CrossCoreSetFlag` / `CrossCoreWaitFlag` 握手，两级双缓冲重叠搬运与计算。

## 三个值得带走的结论

### 1. 可以把一次提交当测量仪器

评测平台只返回 15 个耗时，不说形状、不说走了哪条分支。
在二十多个版本里，第 8–12 点对我们所有改动**完全没有反应**（跨版本波动仅 ±2%），
却查不出原因。

解法是给每条分发路径的内核入口插入一段**几何间距**的空转
（第 k 条 `h_k` 个单位，h ∈ {1, 2, 4, 8, 16, 28, 40, 64, 100, 160}）。
空转只做标量累加，使用其结果的分支永不成立，不影响任何输出。
先在本地标定每条路径一个单位值多少微秒，再用线上耗时减去基线查表。

线上逐点耗时跨版本稳定到 0.02%（409.60 对 409.50），而一个单位约 13 微秒，
读数毫无歧义。

结果：**10 个点走通用 Cube 路径，4 个走 row_vector，1 个走 dot。
narrow、small_vector、全 K 常驻这些路径，一个评测点都没覆盖到** ——
而那正是前面很多轮改动的全部内容。

方法细节见 [`docs/14-第14步_路径探针与真实瓶颈.md`](docs/14-第14步_路径探针与真实瓶颈.md)。

### 2. 本地提速不等于线上提速

V63 在本地把某类形状提速 3.85 倍，线上总分反而从 28.01 掉到 27.18 ——
它优化的形状族根本不在评测集里，而它的副作用击中了一个真实评测点。
类似的事发生了三次。

教训是：**在知道评测形状之前，本地加速比没有意义。**
后期改用"指纹法"反查形状 —— 用线上耗时、dtype 和转置组合，
交叉比对候选形状的真机实测值 —— 才把 15 个点逐一锁定，
记录在 [`docs/00-官方15个测试点形状.md`](docs/00-官方15个测试点形状.md)。

### 3. 小形状上，Matmul 库的发射开销就是全部

用"提前返回"的诊断版本逐段切，测出各阶段真实代价：

| 停在哪 | `1×16×64×1024` | `1×1024×1024×256` | `1×8192×8192×32` |
|---|---:|---:|---:|
| 仅内核启动 | 4.54 | 7.02 | 9.42 |
| + tiling / pipe / 全局张量 | 5.16 | 8.46 | 11.48 |
| + 构造 Matmul 对象 | 6.50 | 8.92 | 11.04 |
| + 真正干活 | 13.98 | 20.14 | 177.64 |

更极端的例子：`2×8×8×512` 真正的矩阵乘只占 **0.06 微秒**，
整个内核却花了 19.82 微秒，其中 AIC 标量流水占用 **97%** ——
时间全花在 Matmul 库的指令发射上，不在计算上。

## 被实测否定的方案

每一条都在真机上测过，不是推断。

| 方案 | 结果 |
|---|---|
| Matmul C 输出到 UB（`CType = VECIN`） | 慢 6–7.6 倍（182 μs → 1380 μs） |
| L0C→UB fixpipe | 硬件不支持（arch 2201 只有 GM 和 L1） |
| 放大基本块到 128×256 / 256×128 | 全部更差，64×256 本来就是最优 |
| bn 放宽到 512 | 更差（203 对 184） |
| 缩小基本块换并行度 | 更差（16×16 把 14.8 推到 20.9） |
| 按分块放宽手工 Mmad 路径门槛 | 大幅更差（38 μs → 182 μs） |
| `CopyTiling` 是主要固定开销 | 不是，加载两次只多 0.6–2.2 μs |
| 跳过工作区清零 | 净负 0.49 分 |
| 全局固定 `baseK = 512` | 灾难（179 μs → 658 μs） |
| VECIN 服务模式（早期） | 小形状上慢 3 倍 |
| 不打包 B | 慢 19–21% |

### 工具链

真机在远程服务器上，网关只接受密码认证，无法用密钥免密登录。
`tools/ssh_queue_agent.py` 是常驻的文件队列代理：密码用 `getpass` 交互输入，
只留在进程内存，不落盘不进日志；任务以 JSON 文件投递，结果写回同名 `.out`。

- `tools/shape_scan.py` —— 批量测形状耗时，并记录实际执行的内核符号名
- `tools/nan_bisect.py` —— 形状阶梯上的精度回归，对照 FP64 参考值
- `tools/grid_probe.asc` —— 单进程内测上万个形状（缓存 workspace 与 tiling，
  摘掉每次调用约 875 微秒的 host 开销）

## 没做到的

目标是晋级线前 32 名（约 65 分），最终 114 名、45.84 分。

65 分要求 15 个点**全部**落在全场最优的 1.244 倍以内。
结束时只有 1 个点达标（第 7 点 1.12），另有 2 个接近（1.31、1.33），
其余 12 个在 1.40–2.52 之间。这不是调参能跨过的距离。

最后一小时试过一次"跳过工作区清零"的赌注，实测净负 0.49 分，没有提交。
