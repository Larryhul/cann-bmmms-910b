# BatchMatmulMaxSum on Ascend 910B2

CANN 算子挑战赛参赛记录。算子是 `y[b] = Σ_m max_n (X1[b] · X2[b])[m][n]`：
批量矩阵乘，对每行取最大值，再把这些最大值加起来，每个 batch 输出一个标量。

硬件 Ascend 910B2，CANN 9.0.0，Ascend C 手写内核，`dav-2201` 架构。

**最终成绩：45.84 分，第 114 名（共 646 队），15/15 全部通过。**

这个仓库不只是最终代码，更是两天里 150 多个版本的完整实验记录 ——
包括大量**被实测否定的方案**。后者可能比前者有用。

## 三个值得带走的结论

### 1. 对数计分下，该优化的是已经最好的点

计分是 `100/(1+log_1.5(t/T))`，T 是全场最优。对 `t/T` 取对数意味着
**越接近 TBest 的点，每省一微秒换到的分数越多**。

最终这 15 个点里，第 7 点省 1 微秒值 1.63 分，第 11 点省 1 微秒值 0.021 分 —— 相差 76 倍。
而第 11 点的倍数（1.90）看起来比第 7 点（1.12）"差得多"。

项目前期一直在盯着倍数最差的大点改，那是算错了账。完整的边际收益表在
[`final/RESULT.md`](final/RESULT.md)。

### 2. 用一次提交读出每个测试点走哪条代码路径

官网只给 15 个耗时，不说形状、不说走了哪条分支。在二十多个版本里，
第 8–12 点对我们的所有改动**完全没有反应**（跨 V43→V66 的波动只有 ±2%），
却查不出原因。

解法是把提交本身当测量仪器：给每条分发路径的内核入口插入一段**几何间距**的空转
（第 k 条 h_k 个单位，h ∈ {1,2,4,8,16,28,40,64,100,160}），空转只做标量累加、
分支永不成立、不影响结果。先在本地标定每条路径一个单位值多少微秒，
再用官网耗时减去基线查表。

官网逐点耗时跨版本稳定到 0.02%（409.60 对 409.50），而一个单位约 13 微秒，读数毫无歧义。

结果：**10 个点走通用 Cube 路径，4 个走 row_vector，1 个走 dot。
narrow、small_vector、全 K 常驻这些路径一个点都没覆盖到** ——
而那正是前面很多轮改动的全部内容。

方法细节：[`docs/14-第14步_路径探针与真实瓶颈.md`](docs/14-第14步_路径探针与真实瓶颈.md)

### 3. 910B 没有 L0C→UB 的 fixpipe

算子的归约需要把矩阵乘的中间结果 C 从 L0C 搬出来做 max。
自然的想法是直接搬进 UB，省掉显存往返。

查 CANN 头文件 `kernel_operator_fixpipe_intf.h`：`__NPU_ARCH__ == 2201`（910B）
只提供 L0C→GM 和 L0C→L1 两种目的地，**L0C→UB 只在 310 系列（3002/3102）上存在**。

这解释了为什么 Matmul API 的 `CType = VECIN` 在 910B 上要绕 KFC 服务模式，
以及实测为什么慢 6–7.6 倍（`1x8192x8192x32` 从 182 μs 变成 1380 μs）。

C 必须落显存。这是硬件约束，不是优化不到位。

## 被实测否定的方案

每一条都在真机上测过，不是推断。

| 方案 | 结果 |
|---|---|
| Matmul C 输出到 UB（CType=VECIN） | 慢 6–7.6 倍 |
| L0C→UB fixpipe | 硬件不支持（arch 2201） |
| 放大基本块到 128×256 / 256×128 | 全部更差，64×256 本来就是最优 |
| bn 放宽到 512 | 更差（203 对 184） |
| 缩小基本块换并行度 | 更差（16×16 把 14.8 推到 20.9） |
| 按分块放宽手工 Mmad 路径门槛 | 大幅更差（38 → 182） |
| CopyTiling 是主要固定开销 | 不是，加载两次只多 0.6–2.2 μs |
| 跳过工作区清零 | 净负（小点慢 7–12%） |
| 全局固定 baseK=512 | 灾难（179 → 658） |
| VECIN 服务模式（早期） | 小形状上慢 3 倍 |
| 不打包 B | 慢 19–21% |

## 固定开销的实测分解

用"提前返回"的诊断版本逐段切，测出各阶段真实代价：

| 停在哪 | `1x16x64x1024` | `1x1024x1024x256` | `1x8192x8192x32` |
|---|---:|---:|---:|
| 仅内核启动 | 4.54 | 7.02 | 9.42 |
| + tiling / pipe / 全局张量 | 5.16 | 8.46 | 11.48 |
| + 构造 Matmul 对象 | 6.50 | 8.92 | 11.04 |
| + 真正干活 | 13.98 | 20.14 | 177.64 |

MIX 内核（AIC+AIV）光启动就要 4.5–9.4 微秒，AIV-only 内核只要 1.26 微秒。
对最小的几个测试点来说，TBest 本身就只有 1.2–2.5 微秒 —— 启动开销就是全部战场。

小形状上 Matmul 库的发射延迟同样触目：`2x8x8x512` 真正的矩阵乘只占 0.06 微秒，
却花掉 19.82 微秒，其中 AIC 标量流水占用 97%。

## 仓库结构

```
final/      V133 的内核源码，以及官网逐点成绩、形状表、边际收益表
docs/       27 篇编号工程笔记（按时间顺序）+ 索引
tools/      远程真机测量工具链
history/    10 个里程碑版本的源码 + 全部官方成绩记录
```

`docs/` 里的笔记是当时写的，保留了判断错误和修正过程，没有事后美化。
`history/` 只保留拿到过官方成绩的里程碑版本；开发期间共产生 150 多个版本，
其余是中间态，不在仓库内。`history/official_scores.json` 记录了全部 12 次
有官方成绩的提交，含逐点耗时与当时的 TBest。

### 工具链

真机在远程服务器上，网关只接受密码认证，无法用密钥免密。
`tools/ssh_queue_agent.py` 是一个常驻的文件队列代理：密码用 `getpass` 交互输入，
只留在进程内存里，不落盘不进日志；任务以 JSON 文件投递，结果写回同名 `.out`。

- `tools/shape_scan.py` —— 批量测形状耗时，并记录实际走的内核符号名
- `tools/nan_bisect.py` —— 形状阶梯上的精度回归，对照 float64 参考
- `tools/grid_probe.asc` —— 一个进程内测上万个形状（缓存 workspace 和 tiling，
  把每次调用约 875 微秒的 host 开销摘掉）
